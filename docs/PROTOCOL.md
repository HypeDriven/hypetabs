# Local browser protocol v1

The Chrome extension connects to `com.hypetabs.bridge`. The native bridge validates Chrome's caller origin against the exact registered extension origin and relays messages through a named pipe scoped to the Windows user SID. The pipe DACL allows only that user and rejects remote clients. No TCP or HTTP listener exists. Same-user native processes are inside the local trust boundary; the origin argument is not an authentication boundary against malware already running as that user.

Both transports use a four-byte little-endian unsigned UTF-8 JSON byte count followed by the JSON payload. Frames are limited to 65,536 bytes. Protocol objects are flat and allow only string, integer, and boolean values; arrays, nested objects, nulls, duplicate keys, invalid Unicode, and floating-point numbers are rejected. At most 16 properties are allowed. Unknown message types, version mismatches, and invalid state transitions disconnect the profile.

Limits: 16 simultaneous connections, 10,000 indexed open tabs total, 10,000 staging records per connection, 256 queued inbound frames, 128 queued outbound frames, and 5,000 incoming messages per connection per second. Backpressure waits at most five seconds; outbound writes time out after two seconds. Idle pipe reads sleep on Windows events and shutdown cancels pending I/O.

Every message includes `v: 1` and a `type` string. Transport-assigned connection generations scope all transient identifiers; the extension cannot choose that generation.

| Direction | Type | Additional fields / meaning |
| --- | --- | --- |
| Extension → host | `hello` | `profile`: persistent lowercase UUID in profile-local extension storage; `label`: up to 128 UTF-8 bytes. Must be first. |
| Host → extension | `setLabel` | `label`: nonempty profile name, at most 32 UTF-16 code units, with no control characters. Saved only in the receiving Chrome profile. |
| Extension → host | `label` | `label`: acknowledged saved name. Updates the profile's open, staged, and retained tab search labels. |
| Extension → host | `labelError` | No additional fields. The profile could not persist its new name. |
| Host → extension | `collect` | `enabled`: boolean; `history`: whether closed-tab collection is enabled; `since`: persisted clear-data cutoff in epoch milliseconds. Enabling requests a fresh snapshot; disabling stops collection. |
| Extension → host | `begin` | Start an atomic profile snapshot. |
| Extension → host | `upsert` | `id`, `window`: nonnegative 32-bit integers; `title`: up to 4,096 UTF-8 bytes; `url`: up to 8,192 bytes; `used`: nonnegative safe-integer timestamp; `incognito`: must be false. Applies to the snapshot while one is in progress, otherwise updates live state. |
| Extension → host | `end` | Replace only this profile's open tabs with the completed snapshot. |
| Extension → host | `remove` | `id`: remove an observed open tab. This represents a missing tab without proof of closure. |
| Extension → host | `close` | `id`, `closed`: observed closure timestamp in milliseconds. Converts an existing open record into retained closed metadata. |
| Extension → host | `recent` | `session`, `title`, `url`, `closed`, `incognito: false`: a browser-provided recent closure. Unambiguous observed/imported pairs are associated; ambiguous matches use URL fallback. |
| Host → extension | `restore` | `request`, `session`, `url`: reopen in the receiving profile. Only a revalidated individual-tab session is restored; otherwise reopen the complete HTTP(S) URL. |
| Host → extension | `activate` | `request`: positive correlation ID; `id`: selected tab; optional `guided: true` requests a location notification; the host sends it for guided cues and also in direct mode on an unscaled desktop so it can confirm actual Windows foreground. The extension revalidates the tab, rejects incognito, activates it, resolves its window again, then requests focus. |
| Host → extension | `prepare` | `request`, `id`: select a non-incognito tab without requesting window focus. Re-read the tab after obtaining window bounds; require it still active in that window. Guided search issues this before taskbar discovery when the desktop satisfies the validated window-matching scale policy. |
| Extension → host | `prepared` | `request`, `title`, `left`, `top`, `width`, `height`: same bounds and title limits as `located`, with all bounds required. A successful preparation sends this response alone; failure sends `result: unavailable`. It does not claim browser focus or establish a native HWND. The host requires a matching outstanding preparation request, connection, deadline, and uncancelled cue generation before starting taskbar discovery. |
| Extension → host | `display` | `index` (0-based), `count` (1–16), `left`/`top` (−100,000 through 100,000), `width`/`height` (1 through 32,768), `dpi` (48 through 960), `primary` (boolean). One message per display from `chrome.system.display.getInfo()` after `hello` and on `onDisplayChanged`; the host stages a sequence starting at index 0 and adopts it when the final index arrives. Chrome DIP bounds; the host matches them to physical monitors by DPI, primary flag, scaled size, and nearest center, rejecting ambiguous layouts. Optional: without it only 96-DPI geometry is used. |
| Extension → host | `located` | `request`, `title`: current title bounded like `upsert`, plus integer browser-window bounds `left`, `top` (−100,000 through 100,000), `width`, `height` (1 through 32,768). Emitted before `result` only after successful guided activation, reported browser focus, and valid bounds. Legacy messages without all four bounds remain accepted but cannot initiate a cue. Partial bounds are rejected. This is a discovery hint requiring native verification. |
| Extension → host | `result` | `request`; `status`: `ok`, `focus`, `restored`, or `unavailable`. The host accepts responses only for its outstanding request on the matching connection. |

Disconnects leave visible tabs labeled unavailable until a complete new snapshot arrives. They do not make old tab IDs valid under a new connection. Browser errors and tab metadata are not logged. Closed entries have separate persistent record identities and reconnect by profile identity rather than obsolete tab IDs. Successful correlated restoration consumes that closed entry. Stored closed metadata is protected by Windows DPAPI; no open-tab snapshot is persisted.

For post-activation guidance, the host currently requires every monitor at 100% scaling and exactly one visible, non-minimized Chromium-class window with matching physical bounds. It then verifies that window's Chrome process and foreground status before bounded tab-header discovery. Ambiguous geometry, unsupported scaling, or absent bounds retain direct activation without an arrow; titles alone never identify the native window.

Each request expires ten seconds after it is queued, using the host's monotonic clock. `located` and `result` messages arriving at or after that deadline are ignored even if Windows has not delivered the timer callback yet. Expiration affects only due requests; later requests retain their own deadlines. A timeout does not prove that Chrome performed no action, so recovery asks the user to search again and check the result rather than automatically resending restoration.

For taskbar-first guidance, the host queues native discovery on a background worker after a valid `prepared` response. If discovery succeeds and native window identity still matches, the cue waits for release over the taskbar target and foreground activation of that window. The host then sends a fresh `activate` request with `guided: true`, revalidating the browser tab before post-activation tab-header discovery. Failed preparation or unavailable discovery uses a fresh activation request directly. Cancellation, expiry, disconnect, and Clear saved data suppress pending guidance. No restoration command is automatically retried by this flow.
